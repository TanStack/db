1. **Admission is a self-asserted record unless authority exists outside the record.**
   - **Broken claim/link:** PC4-09, M11, and R12 claim that an agent cannot authorize its own trust roots and that commands are capability-checked. Yet none of M01–M12 represents an authenticated principal, authority scope, capability source, or verifier independent of the proposed `AdmissionRecord`.
   - **Exact evidence:** `MODEL.md:103-112` defines M11 as “an authority act”; `MODEL.md:227` says commands are capability-checked. `PROCESS.md` C05 leaves admission as code review, signed manifests, a local authority file, “or another project-owned mechanism.” S01 says admission governance is absent (`tanstack-trust-rfc-v0.3.md:549-562`) and authentication is absent (`:629-635`). S08 explicitly describes a trusted local process that does not authenticate records (`kernel.ts:187-190`).
   - **Failure observation/consequence:** If the same process can submit a proposal and a schema-valid record naming a maintainer as authorizer, no modeled relation distinguishes self-authorization from a legitimate admission. The record proves only that admission-shaped data exists, reproducing the schema-validity/authority collapse that PC4-09 forbids.
   - **Possible repair condition:** Add or trace an independently anchored principal/capability/authority relation and require admission transactions to verify it against proposal provenance. If that enforcement is deliberately outside this grammar, weaken PC4-09 to an unenforced boundary and name the external contract.

2. **M01 cannot be both immutable and contain later supersession/admission facts.**
   - **Broken claim/link:** M01 is an “immutable envelope” that retains supersession and admission references, while PC4-06 and M11 require later admission, revocation, and supersession to append without rewriting history.
   - **Exact evidence:** `MODEL.md:24-29` places creation time, supersession, and admission reference in the immutable envelope. M11 at `MODEL.md:103-112` permits later admit/revoke/supersede acts. S04 instead supports immutable observations plus separate append-only challenges, admission/policy records, and explicit supersession (`protocol-donor-perturbation.md:140-145`).
   - **Failure observation/consequence:** Create claim v1, then admit it and later supersede it with v2. Either v1’s envelope mutates to acquire those references, violating immutability, or it remains unchanged and cannot recover the current admission/supersession relation promised across interfaces.
   - **Possible repair condition:** Separate immutable definition/envelope facts from append-only `AdmissionRecord` and `SupersessionRecord` edges; derive a current envelope projection at a named snapshot.

3. **Concrete failure scene: executable local modules can make a supposedly side-effect-free snapshot read change the world and its own answer.**
   - **Broken claim/link:** M02 permits ordinary code modules containing applicability and presentation functions, while X06 and R12 promise coherent snapshots and side-effect-free queries.
   - **Exact evidence:** `MODEL.md:36-41` lets modules export applicability functions and messages; `MODEL.md:185-191` and `:227` require coherent snapshots and pure reads. S01 says the stable extension boundary is not exposed (`tanstack-trust-rfc-v0.3.md:171-175`) and hidden-input treatment is unresolved (`:843-848`). S08 registers trusted executable rule functions and has no sandbox (`kernel.ts:46-51`, `:187-190`).
   - **Failure observation/consequence:** A project-local applicability function reads `Date.now()`, `process.env`, or mutable module state and increments a counter. Two `report(snapshot=S)` calls return different applicability/conditions, and the first read changes the second. The snapshot is neither coherent nor side-effect-free even though its stored revision is unchanged.
   - **Possible repair condition:** Require semantic hooks to be pure over captured inputs, execute them in an isolated dependency-capturing boundary, or persist their evaluated result as part of the snapshot. A read must refuse evaluation when an input cannot be frozen.

4. **Monotonic revision identity defeats domain-owned applicability and makes harmless reversions irrecoverable.**
   - **Broken claim/link:** M08 says applicability is domain-owned, but also states that returning to old bytes never revives an old revision; UC02 treats any dependency/config revision change as expiry.
   - **Exact evidence:** `MODEL.md:85-90`; `PROCESS.md:55-65`. S01 calls exact byte identity only a conservative boundary, says the public applicability contract is unresolved, and warns that capture is only as complete as dependency discovery (`tanstack-trust-rfc-v0.3.md:307-358`). S08 hard-codes applicability to exact current revision and fingerprint (`kernel.ts:559-566`) and states old bytes cannot reactivate evidence (`README.md:103-106`).
   - **Failure observation/consequence:** Change a semantically irrelevant config comment, then revert it. The domain matcher can establish equivalent applicability, yet the monotonic revision rule either forbids reuse anyway or becomes merely historical bookkeeping contrary to UC02’s stale-state reconstruction. Reversing the change cannot restore the pre-change state without rerunning every affected method.
   - **Possible repair condition:** Keep monotonic revisions for history while making applicability a separate, explicit, admitted equivalence judgment. Specify when exact revision equality is mandatory and when a domain-certified relation may reuse evidence.

5. **Exact same-law/same-case repair creates an escape hatch or a permanent dead end across versions.**
   - **Broken claim/link:** R10 requires same-law/same-case repair, while the model also requires versioned claims and leaves identity relations unresolved.
   - **Exact evidence:** PC4-04 requires unresolved identity relations to remain explicit; M10 and R10 are at `MODEL.md:96-102` and `:225`. S01 says exact replay is deliberately narrower than useful repair and leaves cross-version mapping unresolved (`tanstack-trust-rfc-v0.3.md:395-403`, `:828-839`). S08 uses exact canonical JSON identity and acknowledges semantic equivalence is a package obligation (`kernel.ts:106`, `:514-538`).
   - **Failure observation/consequence:** Fixing the checker or law requires claim v2. If v2 has a new identity, its passing replay cannot repair v1’s challenge, leaving a permanent contradiction. If the author keeps the old identity to enable repair, history falsely says the same law ran. Conversely, an adversary can rename a law/case to strand a counterexample.
   - **Possible repair condition:** Define an authorized cross-version identity/morphism that states which obligation and counterexamples carry forward, defaulting unresolved mappings to preserved challenge visibility rather than silent escape.

6. **“Low confidence becomes a policy-free condition” is impossible while threshold ownership is unresolved.**
   - **Broken claim/link:** X02 is one policy-free condition model, but UC08 says a low-confidence probabilistic result becomes a condition while the domain/action threshold boundary remains open.
   - **Exact evidence:** `MODEL.md:160-166` defines X02 as policy-free; X05 at `:183-187` assigns action to profiles. `PROCESS.md:118-119` turns low confidence into a condition, while C04 at `PROCESS.md:222-224` and `EVIDENCE.md:137` leave semantic-versus-action threshold ownership unresolved.
   - **Failure observation/consequence:** The same evaluator returns 0.87. A development profile permits action above 0.80; CI requires 0.95. A single shared “low confidence” condition cannot be both present and absent. Making it profile-specific violates X02; choosing one threshold silently assigns policy to the semantic layer.
   - **Possible repair condition:** Require an admitted domain adequacy rule to derive evidence conditions, and let policy thresholds derive only profile-specific actions. Every threshold must carry owner, version, scope, and provenance.

7. **Rule disablement has no modeled disposition for an already-open condition.**
   - **Broken claim/link:** M03 says configuration determines active obligations and cannot conceal conditions from earlier revisions; R13 says `off` changes the obligation set; X02 lacks an explicit active/historical/terminated lifecycle.
   - **Exact evidence:** `MODEL.md:45-53`, `:162-166`, `:228`; `BRIEF.md:51-54`; PC4-06 requires condition lifetime to remain distinct. E-I05 admits the suppression classification is partly unresolved (`EVIDENCE.md:83-86`).
   - **Failure observation/consequence:** An endpoint has an open counterexample and the project changes its rule to `off`. If the condition disappears from current reads, M03’s non-concealment promise fails. If it remains current, `off` did not change the active obligation set. If it remains only with severity `off`, configuration/policy has changed the meaning of the supposedly policy-free condition.
   - **Possible repair condition:** Model condition occurrences with validity intervals and explicit disposition reasons, and distinguish current-obligation queries from historical-condition queries. Define what disablement terminates and what challenge history remains visible.

8. **Atomic commit of the returned array does not establish that the array is complete or prevent favorable submission.**
   - **Broken claim/link:** M07/R06 claim callers cannot submit only favorable findings, but F02 exposes an observation-batch submit command and there is no modeled commitment tying that batch to the method’s complete production output.
   - **Exact evidence:** `MODEL.md:78-83`, `:221`, and F02 at `:297-303`. S08 says the checker and producer are trusted inputs and accepts any returned findings array (`kernel.ts:410-464`), including an empty or selectively shortened array. S09 distinguishes a partial oracle from a complete promise and requires evidence that the comparison rejects the relevant wrong answer (`GUIDE.md:26-41`, `:239-276`).
   - **Failure observation/consequence:** A method produces one failing and one passing finding; the submitter sends only the pass in a schema-valid batch. Alternatively, a compromised method returns only the pass. Atomicity faithfully commits the favorable subset, so the claimed anti-cherry-picking property never fires.
   - **Possible repair condition:** Bind submission to a method-run receipt containing a batch digest, declared subject universe/cardinality, reach witness, and omissions; reject detached partial submission for executable methods or label it as a separately admitted inspection with narrower coverage.

9. **The shared-adapter claim is supported by a model restatement while the traced implementation exhibits semantic drift.**
   - **Broken claim/link:** PC4-11, X04, and R14–R16 claim consistent projections with stable codes, causes, limits, legal actions, and policy-derived severity.
   - **Exact evidence:** `EVIDENCE.md:36` maps PC4-11 to all use cases, but the control is explicitly “Model pass, not executed API test” (`EVIDENCE.md:115`). S08’s LSP hard-codes severity from assessment status and uses that status as the diagnostic code (`lsp-server.mjs:20-26`); its only action is “Reassess evidence claim” (`:103-109`). S01 records package discovery, registration, generic ingestion, typed explanation, and work as absent (`tanstack-trust-rfc-v0.3.md:589-606`) and says the severity mapping is adapter behavior, not policy (`:608-618`). S04 warns that all adapters may share a defective service (`protocol-donor-perturbation.md:152-156`).
   - **Failure observation/consequence:** Project the current Endpoints state through LSP and CLI/MCP. LSP emits `supported/contradicted/unresolved` codes and fixed severities without M12 provenance, affected uses, coverage limits, or typed legal operations. The adapters cannot recover X04 from the traced service without adding new semantics.
   - **Possible repair condition:** Provide executable cross-adapter conformance fixtures over one frozen snapshot, including condition identity, policy provenance, legal actions, and version/cursor. Until then, label X04–X06 as unsupported proposed structure rather than source-reconstructed projection.

10. **Transactional receipts omit retry identity, leaving an indeterminate duplicate-run window.**
    - **Broken claim/link:** M09 claims to separate acceptance, delivery, cancellation, process result, reach, validation, commit, and receipt; R12 claims transactional discriminated receipts, but no idempotency or attempt correlation relation appears.
    - **Exact evidence:** `MODEL.md:92-97`, `:227`. S04 says commands require delivery/receipt, authorization, cancellation, and transaction outcomes (`protocol-donor-perturbation.md:164-169`). S01 still lists transactions between dependency update and check reach as open (`tanstack-trust-rfc-v0.3.md:866-871`). S08 serializes requests but exposes no expected version, capability, idempotency key, or receipt state (`service.mjs:45-126`).
    - **Failure observation/consequence:** A method reaches production and commits, but the response is lost. The agent retries. The method executes again and appends duplicate observations or repeats an external effect; the client cannot tell “first committed, second duplicated” from “first never ran.”
    - **Possible repair condition:** Give every command an idempotency key and separate intent, attempt, effect, commit, and delivery identities. Declare which methods are retry-safe and require explicit reconciliation for indeterminate outcomes.

11. **The frozen source trace is not reproducible for several consequential inputs.**
    - **Broken claim/link:** The candidate presents an exact-equivalence frozen extraction with a source trace, but S02, S05, and S06 cannot be recovered as frozen source bytes from `sources.json`.
    - **Exact evidence:** `sources.json` gives S02 only a Field Log run/event ID and no path/hash; S05 only a mutable URL and vendor-content limit; S06 only event IDs and a paraphrased description. Yet `EVIDENCE.md:16-24` assigns them consequential roles in the primitive baseline, probabilistic evaluator structure, and linter-shaped requirement.
    - **Failure observation/consequence:** A fresh auditor cannot verify whether the exact S02 design, S05 article version, or S06 wording supports the frozen claims. A changed vendor page or inaccessible event can produce the same trace metadata while containing materially different language.
    - **Possible repair condition:** Preserve immutable snapshots or content hashes for every consequential source, and include the exact user requirement text or a frozen signed excerpt where source access is intentionally restricted.

12. **The ablation control proves dependence on its own vocabulary, not minimality of the decomposition.**
    - **Broken claim/link:** The process claims every retained unit is necessary and that no additional form survived, but use cases and preservation mappings are written directly in M/X identifiers and ablation removes units without testing merge or substitution.
    - **Exact evidence:** `EVIDENCE.md:115-116` calls reconstruction and ablation model passes. `PROCESS.md:147-149` concludes no retained item can be removed; `PROCESS.md:211-213` says no additional form survived. UC01–UC08 are narrated almost entirely as sequences of M/X units. S09 warns that a model can omit a meaningful distinction and that controls must distinguish it from a weaker model (`GUIDE.md:72-79`, `:104-108`, `:239-257`).

    - **Possible repair condition:** Restate use cases in source-level behavior rather than candidate identifiers, then test at least one merge/substitute decomposition and record a concrete distinguishing history for each claimed primitive boundary.

## Controls

- Fresh auditor context contained one frozen candidate only. No sibling candidate, audit, Field Log, prior review, preferred outcome, or earlier assistant discussion was inspected.
- The assay assumed failure and used only PC4-01–PC4-12 and the candidate’s declared Endpoints/API scope.
- Local hashes for S01, S03, S04, all listed S08 files, and S09 matched `sources.json`.
- Prototype discrepancies are used as support defeaters, not as a demand that every proposed API already be implemented.
- List order is not a ranking. Repair conditions are possible falsification/repair boundaries, not architecture selections.
- The hostile stance can turn underspecification into apparent contradiction; each item therefore names the concrete observation that would distinguish a harmless omission from an actual failure.

## Coverage limits

- No cross-domain generality attack was made; the candidate already declares range untested beyond Endpoints.
- No API tests were executed. The review is a static hostile assay of the frozen model and its exact traced sources.
- S02 was not inspectable from its trace without entering prohibited Field Log material. S05 was not fetched, and S06 event records were not inspected.
- Source files not named by exact paths in `sources.json`—including prototype tests, storage internals, and linked companion documents—were not inspected.
- The Field Log, every `audits/` directory, sibling candidates, and all other reviewer/agent output remained unseen.
