## Recovered losses

### OG-01 — Named execution evidence omits settlement and pruning comparisons

- **Guide:** lines 21–26, 106, 241–251, 284: distinguish the production path, comparison execution, and sensitivity for the promised observation.
- **Candidate:** `O/evidence.mjs:102–117` records witnesses only through `check`; `O/compiled-dependencies.mjs:238–245,278–285` uses ordinary assertions for settlement, catalog exclusion and expected read counts; `O/dependencies.mjs:326–350` does the same for rejection, read obligations and unaffected envelopes; `O/driver.mjs:589–593,619–633,644–668` does so for pending settlement, retries and transaction outcomes. The compiled final report (`integrated-todo/evidence/oracle-repair-compiled-final/report.json:21–30`) has named baseline/optimistic/settled-row witnesses, but none for these other comparisons.
- **Gap:** The report can identify row comparisons individually but cannot independently establish that its settlement, retry, pruning and envelope assertions ran. Operation/read totals are not named assertion-execution witnesses. The assertions themselves exist and can reject failures; the missing item is their separate execution evidence.
- **Trace:** Comparison instrumentation was added around row equality; remaining correctness assertions stayed in the legacy assertion category. `Evidence.run:159–169` recovers only a stack-site label after an ordinary assertion fails, not positive execution evidence when it passes.
- **Limits:** This does not show an assertion was skipped in any supplied run. The guide does not require instrumenting every mundane assertion; these comparisons are named product/optimization claims in `ORACLE-PLAN.md:93–107,162–166` and `SQL-EFFECT-RULES-PLAN.md:117–122`.

### OG-02 — A released response is credited as delivered without a delivery witness

- **Guide:** lines 155–174, 184–191, 199, 241–243: control and witness the actual boundary a schedule's claim needs; a released Promise is not necessarily applied work.
- **Candidate:** `O/concurrent.mjs:86–105` holds the actual response after `route.fetch`; `203–217` releases a hold, waits 30 ms, checks that outcomes are pending, then names the checkpoint `delivered ..., sibling outcome pending`. The report scope at `65–70` calls this independent response delivery order. The route returns `route.fulfill` after the hold but records no fulfill-completion or client-consumption witness.
- **Gap:** The intermediate pending-state assertion can occur before the released response reaches the client. It cannot distinguish “the response was consumed but settlement correctly waited for a sibling” from “the response has not arrived yet.” The generated `deliveryOrder` controls release order; no retained evidence establishes the claimed client-observed order.
- **Trace:** The event boundary is compressed from release → fulfillment → receipt processing into one hold release plus a fixed delay. Server response arrival is witnessed (`held.arrived`), but the corresponding client delivery/processing boundary is not.
- **Limits:** Static inspection does not establish whether 30 ms was sufficient in the supplied campaign or whether a mutant survives. Source notification checks still protect notifications that were captured. This is a reach gap for the named intermediate delivery checkpoint, not a claim that all schedule checks are ineffective.
