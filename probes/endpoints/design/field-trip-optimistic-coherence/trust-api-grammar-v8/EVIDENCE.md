# Evidence — TanStack Trust: Protocol Discovery and Engineering

## Evidence classes

This extraction keeps six kinds of support separate:

1. **User-owned product direction:** valuable future conditions, native versus
   engineered hardness, generator–verifier composition, project-local discovery
   and an open industry ecosystem.
2. **Executable evidence:** the finite Endpoints decision path, oracle, Trust
   evidence kernel and local interface adapters.
3. **Prior frozen architecture:** run 66's grounding/protocol/hard-point model,
   lifecycle graph, authority distinctions and source record.
4. **Agent observations:** six isolated workflow simulations showing that agents
   recover semantic distinctions but invent missing operations and schemas.
5. **Donor transfer:** Protocols Institute hardness/stigmergy research, formal
   systems, model-based testing and ESLint's extension ecosystem.
6. **Analytical inference:** the two-level workshop/runtime split, verifier
   portfolio and concrete TypeScript lowering proposed in this run.

The confirmed preservation contract fixes the intended design. It does not
validate the representative TypeScript or establish that generator–verifier
search will produce valuable protocols.

## Directly grounded paths

### PostgreSQL native hardness

PostgreSQL's constraint machinery can refuse a write. Catalog/compiler tooling
can report the conditions under which that refusal applies. This supports the
native-hardness distinction. It does not show that the proposed PostgreSQL
package discovers every relevant law or that an editor warning creates new
hardness.

### Endpoints derived evidence

`canSkipRefetch` derives `skip`, `refresh` or `unknown` from artifact identity,
collection authority and compiled effects. `endpoints-real.mjs` records the
result as evidence and explicitly lists “the certificate does not enact refresh
policy” as an omission. This supports typed propositions, evidence,
qualification and counterexample-shaped feedback. It directly refutes any
claim that the current certificate is an enacted hard point.

### Generator–verifier analogue

The current property/oracle code generates programs and histories, executes a
production-shaped path, compares against an independent reference, shrinks
failures and retains replay. Fault controls test whether the verifier detects
known broken implementations. This grounds the inner-loop shape and structured
counterexamples. It does not implement LLM generation, clean admission
verification, sealed cases, target APIs or multi-candidate selection.

### Shared interfaces

The current CLI, LSP and MCP adapters dispatch through one local service and
agree on narrow assessment semantics. This supports a shared operation registry
in one process. It does not implement protocol search, cloud capabilities,
registry discovery, Devtools or the representative PE-M13 operations.

## Range and exclusion

Range is **untested**. PostgreSQL, Endpoints, Neon, product requirements,
oracles, linters, protocols research and cloud operations all informed
extraction. None is an independent marginal case.

The grammar excludes a self-authorizing LLM loop, a verifier the generator can
rewrite, score-as-quality, registry-popularity-as-authority, tool
visibility-as-capability, bypassable gates, home-fixture universality and
purpose-free maximum hardness. These are conceptual negative cases, not an
empirical range comparison.

## Claims deliberately not made

- LLM iteration converges to a generally good protocol.
- Passing a verifier establishes more than its declared property, domain and
  captured dependencies.
- Several verifiers are independent because they have different names.
- Hidden or sealed cases alone prevent reward hacking or overfitting.
- A Pareto set removes the need for authorized value judgment.
- A provider operation is safe because its TypeScript type checks.
- Registry publication, installation, usage or popularity grants admission.
- Project-local success transfers to other environments or domains.
- The representative TypeScript compiles or names the final API.
- Neon, protocol search, cloud capabilities, Devtools or deployment-token
  consumption have been implemented.
- Existing prototype controls validate the lifecycle-wide or industry-wide
  architecture.
