# Concept Guide-word Sweep — Preparation

Status: **prepared, not completed**. The Guide-word Sweep requires competent
content reviewers to judge credibility, consequences, safeguards, and actions.
This document supplies the frozen study definition and complete fixed-word
worksheet. Generated deviations are review prompts, not findings.

## Study definition

- **Purpose:** expose conceptual omissions and category mistakes in the
  target/check/protocol/hardness model before stabilizing the public API.
- **Design intent:** Trust helps teams find hardness by defining valued targets,
  recursively composing typed checks into a DAG, evaluating candidate changes
  through that same DAG, compiling concrete outputs, and connecting those
  outputs to runtime behavior. The whole repeatedly enacted arrangement may
  constitute a protocol.
- **Lifecycle stage:** conceptual design with one finite Endpoints evidence
  kernel; most target, check, variant, artifact, runtime, and target-report APIs
  remain proposed.
- **Success condition:** a new programmer can reconstruct the major concepts,
  their boundaries, and one Endpoints example without relying on the history of
  this Field Log.
- **Safe limits:** no universal hardness score; no claim that a TypeScript
  declaration alone is a protocol; no favorable evidence from hypothetical
  values; no authority inherited from output shape, package installation, or
  agent confidence.
- **Excluded:** incremental scheduling algorithms, cache implementation,
  distributed execution, transport design, hostile package isolation,
  authentication, persistence engine selection, and UI styling.
- **Current records:** the Protocol Institute survey, donor reading, v8 design
  grammar, Term Scan 68, the target/check composition corrections, the Endpoints
  effect verdict, and the evidence-base prototype.
- **Action authority:** Kyle owns product and naming choices. No remediation is
  assigned or closed by this preparation.

## Nodes and parameters

| Node | Intent | Parameters to challenge |
|---|---|---|
| Target | Preserve the valued future that organizes work and serve as a root over composed checks | identity, owner, subjects, checks, preferences, horizon, unacceptable outcomes, preset membership |
| Check | Establish one conclusion from typed inputs or recursively composed child checks | identity, conclusion, inputs, children, combinator, unknown propagation, evidence, outputs, replay |
| Variant evaluation | Test many hypothetical changes without mutating reality | base snapshot, patch location, type, batch isolation, authority, comparison, admissibility |
| Data path | Turn contact with reality into explicit checked results | sources, analyses, checks, oracles, dependencies, unknowns, coverage, provenance |
| Output path | Materialize results for later use | output schema, artifact identity, dependencies, assumptions, validity, consumer |
| Runtime integration | Make compiled results affect behavior | destination, timing, build identity, decision, fallback, failure, refresh |
| Target report | List the concrete methods assembled around a valued future without scoring their overall sufficiency | evidence, checks, gates, integrations, incidents, time, unknowns, fallback, challenge, revision |
| Protocol system | Describe the whole repeatedly enacted coordinating arrangement | participants, roles, rules, artifacts, uptake, infrastructure, maintenance, exception, exit |
| Agent/work projection | Turn gaps and failures into useful iterative work | finding, counterexample, legal action, todo, lease, progress, authority |
| Package composition | Let general and local mechanisms compose without authority leakage | ownership, version, namespace, admission, capability, extension, override |

## Fixed guide-word worksheet

Every cell is a prompt requiring reviewer disposition as credible,
information-needed, not credible with reason, or not applicable.

| Node | No | More | Less | Part of | As well as | Reverse | Other than |
|---|---|---|---|---|---|---|---|
| Target | no explicit valued future | competing targets or presets apply | target omits horizon or owner | only some required checks are retained | hidden preference becomes a required check | a child result rewrites the target | proxy target replaces the human goal |
| Check | no path establishes the conclusion | overlapping composites double-count one result | child evidence, limits, or unknown state is dropped | only one affected branch is reevaluated | evaluation causes undeclared side effects | desired target status determines a child result | workflow advice or agent confidence is mislabeled as a checked conclusion |
| Variant evaluation | no frozen baseline | variants interfere or multiply unboundedly | patch lacks enough context | only one dependent node recomputes when more are affected | real writes accompany hypothetical evaluation | hypothetical result is committed as authoritative | derived verdict or authority is injected as an input |
| Data path | no source, dependency, or unknown state | duplicated/correlated checks appear independent | analysis loses scope or provenance | evidence covers only part of the subject | a source also controls the system it measures | conclusion determines the observation | package output substitutes for domain truth |
| Output path | no materialized output | conflicting artifacts for one build | packet omits assumptions or dependencies | artifact contains only favorable results | output carries undeclared authority or capability | consumer result is used to justify its own certificate | matching shape substitutes for the intended production route |
| Runtime integration | no consumer changes behavior | several consumers interpret one artifact differently | integration checks less than the artifact requires | only server or client enforces a shared invariant | stale build or policy is used as well | runtime decision contradicts the supported result | diagnostic or UI display is mistaken for enacted behavior |
| Target report | no account of what supports the goal | evidence volume is presented as more hardness | report omits incidents, gaps, time, or adaptive paths | only favorable methods are listed | an overall grade appears alongside heterogeneous evidence | team judgment is replaced by system judgment | the report is mistaken for proof that the goal is sufficiently hardened |
| Protocol system | no repeated uptake or maintenance | every graph fragment is called a protocol | declaration omits roles, infrastructure, or exit | only technical code is modeled | informal practice diverges from the declaration | participants route around the intended coordination | installed package is mistaken for a live protocol |
| Agent/work projection | no actionable feedback | duplicate todos amplify activity | finding lacks preserved successes or limits | task closes only part of the semantic gap | work state is counted as evidence | agent changes checker or authority to make work pass | popularity or repeated attempts substitute for progress |
| Package composition | no ownership or admission boundary | overlapping packages redefine the same meaning | package strips limits during reuse | only part of a foreign identity is preserved | capability grant accompanies semantic import | extension weakens its parent requirement | provider identity substitutes for source or domain authority |

## Shared-control and human-factor questions

1. Can a new programmer distinguish the target/check DAG from the larger
   protocol lifecycle without another diagram?
2. Do target roots and recursively composed checks preserve shared dependencies
   without implying a tree or double-counting reused evidence?
3. Which nodes are legal hypothetical injection points, and can a synthetic
   replacement ever become admissible evidence?
4. Is the runtime packet a generic artifact, a certificate, or several artifacts
   with different server/client authority?
5. What observations establish that a declared arrangement is actually an
   active protocol rather than installed code?
6. Can the target report preserve heterogeneous evidence and hardening methods
   without implying that Trust can prove or quantify overall hardness?
7. Who can approve targets, checks, external capabilities, runtime
   integrations, and exceptions, and where do those authorities differ?
8. Does the newcomer explanation remain true for latency gates, product
   requirements, and non-Endpoints examples?
