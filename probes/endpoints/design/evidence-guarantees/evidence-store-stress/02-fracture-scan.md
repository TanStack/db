# Fracture Scan: evidence-backed endpoint assessments

Instrument: fracture-scan. Status: complete, bounded.
Target, frozen premises and success rule: [00-brief](00-brief.md).
Sources S1–S5 retain their original status. No source framework's entire feature
set is imposed on Endpoints. No production defect was reproduced here.

## Position reconstructed

Claim: retaining scoped support for endpoint requirements and deriving concrete,
ordered issues lets later agents improve the system without confusing unknowns,
observed defects or optimization opportunities. Protected insight: ordinary
code plus accumulating, reusable evidence can provide stronger guidance without
a restrictive language or hidden compiler edits.

The following test constructions hold that goal and the brief's eight premises
fixed. They challenge underspecified inference/ordering links, not the existence
of evidence storage itself. They are not assertions that the RFC already makes
the weaker choices; the RFC already names several necessary controls.

## F1 — A passed check is not the requirement it supports

**Route:** internal extension and minimal counterexample.

Trace: permit scoped oracle evidence → record a green real-code test over one
input/history domain → derive an endpoint-level requirement from that result →
present no remaining task for the untested domain. The last step exceeds the
premise that scope must remain meaningful.

Scene: an oracle proves optimized/full-refetch agreement for `apply=false`.
`apply=true` remains a legal production input that invokes another API path.
All receipt fields are honest. If the assessment collapses the receipt to
“dependency coverage passed,” it hides the remaining question.

**Admissibility:** both inputs are in the authored endpoint's domain; the record
is not forged; sampled tests are expressly allowed; the consumer inference is
the only varied freedom. Defeats the claim that descriptive scope storage alone
ensures honest endpoint conclusions. It does not defeat differential testing.

**Preserved insight:** keep a passed check and an unresolved requirement at the
same time. A consumer must match the fact's actual domain to its use. A broader
claim may be supported by several compatible checks, inspection or compiler
facts; there is no requirement that one oracle prove everything.

**Weakening evidence:** a defined consumer rule that already keeps the broader
obligation open or restricts optimization use to the supported input domain
defeats this construction. Then it is a regression target, not an open flaw.

## F2 — Individually valid evidence can form an invalid argument

**Route:** counterexample.

Trace: reusable evidence nodes → composition of several nodes → conclusion that
all needed premises hold. The implication fails without context compatibility.

Scene: a query read bound was inspected against API revision A; a mutation write
bound against revision B. Both are genuine, passing results within their stated
contexts. The deployment assessment joins them because endpoint IDs match.
It claims non-overlap for an execution neither record describes jointly.

**Admissibility:** shared helpers and composites are explicitly in scope. No
unrelated writer or dishonest producer is introduced. The missing relation is
between the contexts of two true claims, not an omitted field in either record.

**Preserved insight:** reuse remains valuable, but joins require compatible
contexts and a traceable rule. Circular evidence cannot manufacture a missing
premise. The endpoint report is a view of shared obligations, not their sole owner.

**Weakening evidence:** exact context compatibility and derivation-cycle controls
in the consumer make the example inadmissible. A single build pin suffices only
if it actually captures the dependencies the two claims rely on.

## F3 — Check-status order can conflict with risk-reduction order

**Route:** internal extension of the assistant's provisional todo order.

Trace: demonstrated bug always before consequential unknown → a minor observed
bug precedes a potentially severe, reachable policy gap indefinitely while new
minor bugs arrive → the queue does not serve its declared risk-reduction goal.

Scene: task A fixes punctuation in a validation message; task B checks whether a
public bulk update enforces ownership for every row. A's failure is reproduced;
B is unknown, with a concrete uninspected accepting path. The proposed categorical
status ordering always puts A ahead of B, independent of impact or safeguards.

**Admissibility:** no probability of exploitation is asserted. Unknown does not
become “broken.” The target is the assistant's rule, not the user's narrower
“bugs > optimizations” heuristic. The brief permits ordering across dimensions.

**Preserved insight:** status, consequence, exposure, existing mitigation and
urgency need separate roles. A high-consequence unknown can produce an urgent
investigation task without being reported as a confirmed vulnerability.

**Weakening evidence:** if the intended ordering already considers those factors
or is merely illustrative, this is an ambiguity to resolve, not a demonstrated
contradiction. No universal numeric risk score follows from the scan.

## Tested claims that did not yield a new fracture

- **Agent weakens the comparator to obtain green:** the RFC already requires
  review of acceptance-control changes, and the oracle guide retains laws,
  method versions and fault sensitivity. Absent enforcement is future design
  work; it is not evidence the stated principle endorses goalpost changes.
- **An endpoint view cannot capture composite guarantees:** false as a critique
  of the frozen position. The RFC explicitly supports composites. The implementation
  still needs shared ownership and projections, but the concept was not omitted.
- **A truthful receipt describes mocked-provider behavior only:** the brief
  allows partial evidence. The fracture occurs only if a consumer credits the
  untested provider premise, already covered by F1.

## Rejected controls

**Outside-standard rebuttal:** “Only formal proofs count, so oracle-supported
optimizations cannot be accepted.” Rejected: the user explicitly values scoped
test evidence. This substitutes a different success standard.

**Vivid near-counterexample:** an unrelated cron job changes PG after settlement
and the endpoint view becomes stale. Rejected as an internal fracture: unrelated
external-write discovery is excluded. A job launched by the endpoint itself is
different and remains the admitted G4 completion boundary.

**Dishonest metadata control:** an agent fabricates a receipt for code never run.
That violates the retained-evidence premise and is not used to defeat the theory.
Authenticity may still require engineering controls; the scan makes no security
claim about hostile repository contributors.

## Limits and handoff

Three candidate fractures identify consumer inference, evidence composition and
task ordering as links needing explicit rules. They are constructed failures of
weaker completions of the theory, not observations that the unimplemented store
has these bugs. The narrower claim survives: scoped evidence and explicit
consumer rules can provide useful guidance without universal proofs.

The method can make underspecification look like a refuted implementation and
can overemphasize memorable failure scenes. The weakening conditions and null
results above constrain that distortion. No prevalence or preferred architecture
is inferred. The separately authorized lifecycle draft will record a candidate
repair; it does not retroactively alter these frozen tests.
