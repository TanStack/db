## Laws and experiments

A complete eager result determines the rows and returned values in its scope.
A later complete, unbounded response can remove an ownerless direct-write row
that it omits. A peer keeps an omitted row alive, but not its old value when the
new result returns that row. Authority: Query's “Direct Writes and Query Sync”
and “Initial Data” contracts, READY-3/PUB-7, and durable acceptance.

The shared startup owner now crosses source-owned and ownerless persisted
provenance, including peer-only rows. Its independent set judgment is unchanged.
Fallback preserves original saved ownership, including its absence. Histories
cross both restore orders, five Query origins, network-first result/fallback,
and a persisting disjoint optimistic insert. Fixed regressions replay the same
model, production driver and comparison as generated histories. The first public
and durable cuts precede refresh; refresh fulfillment and local-only reopen
remain checked. Node and Chromium use the same state names and separately
require every receiving state's reach.

On unchanged production, the first extension fails 72 Query checks on controlled
and real Node SQLite; Chromium reports 34 mismatching startup histories. The
existing driver always gave saved rows source ownership, excluding this law's
ownerless state. The extension also finds a sibling: a peer-only restored row
returned by initialData or cached success gains source ownership but keeps its
old value. Both cases violate the existing complete-result judgment.

An advertised persistence capability must be complete and version-compatible.
An absent optional metadata API and explicit null persistence remain legal.
Authority: `SyncMetadataApi.persistence` and the cross-package protocol contract
in `sync-persistence.ts`. A separate finite oracle owns this structural admission
law; replacement's row-set model cannot judge malformed protocols. It enumerates
nine required members, omission and false-valued corruption, a missing capability,
and three legal forms. Real RxDB and PowerSync invoke sync through the persisted
wrapper on both Node hosts and worker/OPFS. Invalid inputs must report
`InvalidSyncPersistenceCapabilityError` at invocation; legal inputs also complete
a real source result. Unchanged production fails 76 Node admission checks and
38 Chromium checks. Both adapters now validate at sync entry.

The persistence-loss calibration no longer reports success when its clean
candidate fails. It wraps outer and hydration-scoped persistence adapters, counts
actual injected drops, and checks first-result durability before refresh. Separate
before-restore controls require scoped fault reach for RxDB and PowerSync on
SQLite. Query's baseline wait moves its commit outside that scope, so that
counter is not a Query premise. The existing after-deadline controls remain.

## Direct writes and startup work

RR1 describes a real timing change: a successful Query cache entry can precede
its source commit while persisted restore is held. Update/delete then reject
because the row has not loaded. The contract validates against preceding accepted
sync commits, not cache availability. The same-path differential matrix tests
both committed and pre-commit orders. It supplies the causal schedule to the
unwrapped reference, never production's rows or write outcome. Eight new mutants
discard the first result's row writes, commit its metadata transaction, and report
readiness. Each requires positive discarded-row and readiness counters, then
fails that same reference comparison (4 operations through fake storage and real
SQLite). Suppressing the transaction start would test a metadata protocol error
instead, so it is not the final instrument. All 53 direct-write checks pass.
This refutes RR2's specific never-first-commit assertion; it does not turn cache
success into an admission promise.

RR4's added truncate and PowerSync batch retention are real costs. The prior
same-path deterministic SQLite work experiment remains applicable: with empty
or three-row saved baselines and three source rows, both old and current paths
write three source rows. Current snapshot selection adds a clear/metadata reset.
PowerSync retains all snapshot batches; RxDB already used one transaction across
its full initial read. `syncBatchSize` bounds each read, not total snapshot memory.
The snapshot contract permits replacement, and neither adapter consumes persisted
provider resume progress here. Existing one-full-wrapper-row-read laws remain
enforced. No new elapsed-time or bounded-total-memory promise follows. Progressive
publication is a separate product change and is not introduced by this repair.
