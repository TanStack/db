# Explicit SQLite storage targets: oracle review

Reviewed code commit: 6b0192c19924e231049364cd5ef1fde7094245e0
Scope: PR #2069 follow-up for the exported SQLite persistence adapter and its Browser and Electron receiving paths.

The approved law is that an adapter data operation states whether it addresses an eager Collection or a claimed persisted cache generation. A managed target must carry its physical storage ID and claim ID on every read and write. Once that claim is collected, the operation rejects before it can recreate rows, metadata, or catalog state. An explicitly eager Collection may use the same ID bytes; no prefix is reserved. This is a new lower-level API contract, not proof that all third-party adapters honor claims.

The contract-by-history-by-path-by-observation claim is bounded as follows: after a real SQLite claim, write, rotation, and collection, each of eleven core adapter data methods rejects the retired managed target, including through a reopened adapter. At each rejection checkpoint, the old row and tombstone tables and eight per-ID catalogs remain absent. The same test accepts explicit eager reuse of that ID while the managed target still rejects. A Browser coordinator history checks both leader and follower local mutations retain the claim through transaction construction; a real SQLite Browser receiver accepts a claimed mutation and rejects a late one without recreating old storage. An in-process Electron IPC receiver checks target forwarding under protocol v6. The native OPFS tests receive claim and hydration histories but do not enumerate all adapter operations.

Open boundaries: the API still permits a caller to choose an explicit eager target using a retired physical ID. That is the approved escape hatch for arbitrary eager Collection IDs, not an accidental managed fallback. A custom adapter can ignore the target contract, and a direct coordinator caller without a registered managed claim can request eager semantics. Native cross-tab scheduling and real Electron process behavior remain separate receiving cuts in the coverage map. This evidence closes the accidental bare-ID-to-eager adapter fallback for the exercised paths; it does not claim universal cache-generation lifecycle closure.
