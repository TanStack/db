## Law, experiment, and inference

No product-law change needs a decision. A successful complete Query response
replaces that Query's ownership edges, including edges stored in persistence.
An omitted row disappears when no other owner retains it. Another owner's row
and ownership survive. Persistence must retain the resulting rows and ownership.

Authority: [Direct Writes and Query Sync](../../collections/query-collection.md#direct-writes-and-query-sync),
especially successful fetch reconciliation and scope-local omission, together
with the [ownership lifecycle oracle](../../../packages/query-db-collection/tests/ownership-lifecycle.oracle.test.ts).
This does not grant a partial response global omission authority.

The ownership oracle previously exercised persisted ownership, but did not
cross an ordinary eager first success with a held persisted restore.
The [reload oracle](../../../packages/db-sqlite-persistence-core/tests/reload-class-oracle.ts)
correctly covers startup work and ordering. Its eager sources supply local rows;
it does not judge a Query response's replacement of persisted ownership.
The failure was a missing history and receiving-path crossing, not evidence
that those narrower laws were wrong.

The new [shared dimension](../../../packages/db-adapter-conformance/src/persisted-startup-oracle.ts)
uses independent set replacement. It removes the old Query edges, adds the
response's edges, and retains rows with a peer owner. It copies no production
query cache, reconciliation branch, or startup state machine.

Its grammar generates nonempty prior subsets of `a,b,c`, any next subset,
changed values on overlap, optional peer ownership, and either response/restore
order. Empty answers receive extra weight. Each host runs the same property for
40 histories with campaign seed `2367`, then 40 with a random campaign seed.
Four fixed histories also use the same model, production driver and comparison.

The driver holds the actual first baseline row read. Query cache success while
that read remains held establishes the response-first premise. The restore-first
history holds the response until restored rows are visible. It compares:

- Public rows and exact Query ownership after `preload()` fulfills.
- The same observations inside explicit `refetch()` fulfillment.
- Durable rows and ownership after refetch.
- Rows after cleanup and a local-only reopen.

Ownership metadata is read through the Collection's internal metadata store and
the adapter snapshot; public row values use Collection reads. There is no claim
about every intermediate publication or about durable state before refetch.

Controlled storage and real Node SQLite execute generated campaigns. A
[Chromium OPFS receiver](../../../packages/browser-db-sqlite-persistence/e2e/persisted-startup-conformance-oracle.opfs.spec.ts)
executes all four fixed histories through the actual worker and public Browser
persistence factory. It reuses the shared judgment without separate answers.

Unchanged production failed these comparisons before any production edit.
The repair makes the first eager persisted result acquire its durable ownership
baseline, using existing reconciliation machinery. It also preserves ownership
reconstructed by a durable scan before metadata restore publishes. It adds no
new lifecycle state.

### Laws, experiments, and resulting repair

The ownership law remains complete-response set replacement. The Query docs'
“Initial Data” and “Understanding the Data Stores” sections also give complete
initialData and cached Query responses materialization authority. Disabled
fetching or a pending physical fetch does not turn those responses into partial
results. The accepted reload model additionally requires one full row read per
eager tab/run. Its budget law predates this change; it is not a new performance
promise inferred from the faster implementation.

The first repair satisfied membership but scanned durable rows again. Before
changing that production code, the shared ownership grammar gained five origins
(physical fetch, initialData with disabled/pending fetch, and cached data with
disabled/pending fetch), a pre-refetch durable comparison, and a startup work
observation. Controlled storage, Node SQLite, and Chromium OPFS all received
those premises before the production repair. A whitespace-sensitive SQL recorder
initially missed multiline scans. Correcting that recorder and rerunning the
unchanged first repair produced the decisive RED results below. The earlier
false-green recorder runs are not evidence of the work law.

Production now awaits the existing persistence `hydrateBaseline()` capability
before diffing the first eager nonretained result. The wrapper publishes its
already-required full row read and key evidence; Query does not read them again.
Retained revalidations keep their existing scan path. The earlier graph lookup
workaround is removed: restored metadata supplies the peer edges before the
first result applies. No lifecycle state, row-loss waiver, or new product law
was added. The final simplification pass found no further worthwhile proposal.

Captured public/durable cuts and work/premise metrics are checked before later
operations or cleanup. A browser-safe extraction of `withOracleCleanup` retains
the check's error as the aggregate cause and each cleanup error separately.
The nested reopened Collection uses the same helper. It returns callback values
without changing the existing error ordering or resource-release behavior.

The surrounding direct-write oracle exposed a different problem in its own
premise. Query cache success had been treated as proof of a source commit.
During held startup hydration, the new implementation has zero source commits;
update/delete can legitimately reject before any row loads. The public docs'
“Individual Write Operations” rule refers to earlier sync commits, and explicitly
allows missing-row rejection before the first load. The revised driver records
source commits and schedules its nonpersisted reference in the same causal
order. It never derives expected row values from observed production rows.
An explicit held initial-result durable write preserves the committed-before-write
case, alongside the existing later source-write case. The controlled matrix has
24 cases; Node SQLite receives every write operation at all three boundaries,
plus the existing later-refetch ordering cases. This repairs the oracle's timing
assumption without changing its outcome/cache/row/durability comparisons.
