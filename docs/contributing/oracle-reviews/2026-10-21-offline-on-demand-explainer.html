Offline On-Demand Readiness

Why a persisted on-demand query can't render from SQLite while offline today, what we measured, and the one-rule model we're exploring to fix it.

Worktree: .worktrees/progressive-network-first Base: main @ 31dad2dd3 Status: proposal, nothing committed

Where you left off

The report

A Discord user turned on persistence. initialRender: network-first worked for eager collections but not for progressive Electric ones. They expected progressive to render from SQLite without waiting for the network.

Why it fails

Electric reports progressive to core as on-demand, and the persisted wrapper rejects network-first for any on-demand source. Not Electric-specific.

What we measured

Cached rows already show while offline. Only the ready signal waits. A completed progressive sync already works offline; anything short of that waits forever.

Where we landed

One rule: the wrapper may settle a load from SQLite when that exact query finished loading before. Everything downstream follows from existing laws.

How readiness works today

A live query is ready when every source gives it evidence that its rows are present. Since #2115, that evidence depends on the source's sync mode.

EAGER SOURCE

Collection readiness is the evidence

It loads everything without per-query requests, so the query waits for the Collection to be ready. With persistence, a finished SQLite restore of the whole Collection is a separate signal. Network-first (#1955) lets Suspense render that restore after a deadline.

ON-DEMAND SOURCE

A settled load is the evidence

Each query asks for its subset. The persisted wrapper reads that subset from SQLite, then waits for the upstream load. The query is ready when both settle. There is no per-query "restored" signal, so network-first is rejected.

Progressive Electric is on-demand to core. Its Collection stays loading until the full sync, but its queries go ready as their own loads settle.

The wrapper can't tell a complete subset from a partial or never-loaded one; they all just read back as rows. That's why "show whatever SQLite has" is wrong.

The model we're exploring

The one rule
The persisted wrapper may settle a query's load from SQLite once the local rows are visible, if that exact query is covered in the current cache: a previous load of it finished, or the source holds a complete baseline. The network load keeps running and replaces the rows when it answers.
Exact query keyMatches by getLoadSubsetDemandKey. No "this query is broader than that one."exists today
Covered setPer cache generation: keys whose load finished, including empty results, plus "complete baseline" which matches everything.new, in the wrapper
Settle ruleSettle when local rows are visible and the query is covered and the wait has passed or its load failed.new
Network continuesUpstream keeps loading; its rows publish normally when they arrive.exists today

Why it's small: initial readiness, Suspense, queryOnce, skipInitial effects, and ordered-window publication (pagination) all already wait on "this query's load settled." Settle a covered load and every one of them works offline with no live-query changes. ARCHITECTURE.md already says a source that resumes from complete local rows "settles its loads at once." The rule moves that idea from the whole Collection down to one query.

The network-first wait turns into an optional knob. No correctness property needs it. At 0 it matches how a completed progressive resume behaves today.

What the rule settles

The first draft had nine open decisions. Most went away once the design reduced to the single rule.

Where coverage livesThe wrapper, because it has to work the same for every source

Deadline meaning per queryOne wait, measured from each load's start; that load's failure ends it

Page keys built from other rowsA known limit: if restored page 1 differs, page 2 is a miss and waits for the network
Publishing then replacing rowsAlready normal for ready queries
API shapeOne wrapper option: on/off plus wait
Oracle ownerThe wrapper's settle rule; existing live-query oracles own the consequences

Decisions since the first pass

1

Coverage lifetime. Valid until revalidated or until the cache generation ends. A persistedGcTime-style expiry gets its own issue and waits until someone asks for it.

2

The wait. Reuses the network-first option and its 3 s default from #1955; 0 is valid.

3

Mixed joins. On-demand sources register no persisted readiness, so a query that joins an eager source keeps the ordinary readiness path and waits for the eager network offline. That's safe, so it's recorded as a limit.

4

Law and ARCHITECTURE.md. Both are updated in the worktree, along with two glossary terms.

Not done yet: no formal model check, no independent range case, and Electric's own pending load after the wrapper settles is unexamined.
