## Proposed organization and reason

Split the long opening account by observable checkpoint: A admission and rollback isolation; B scheduled attempts/grouping; C cleanup; D transaction settlement. Merge the three built-in cleanup-drain clauses under C, retaining their different clocks and queue-only admission closure. Keep the queue's timing rule separate from its serialization rule. Keep BaseStrategy compatibility separate from built-in rejection signals. Keep harness cleanup outside product cleanup.

No product obligation is intentionally narrowed, strengthened, replaced, or retired. Some language is clarified, while genuinely unresolved source relationships are carried as unresolved. No physical file split is needed: one production driver may feed these judgments. A single generic “cleanup cancels everything” or “every false execute return rejects” law would lose accepted obligations. A universal new admission state machine is unnecessary for this proposal.

## Worked witnesses and old/candidate predictions

1. **Cleanup is not cancellation or flush.** Debounce wait10; call1 at0, call2 at4; cleanup at8 and complete Collection cleanup. At13: no persistence, shared transaction/receipt pending. At14: one call with IDs[1,2], then successful settlement with identical transaction. Old P759–800 and candidate B/C/D agree. A canceled timer, a flush at8, and a new deadline18 all fail different cuts. Throttle's nearby witness uses first call0, non-leading, cleanup4: pending9, start10. The two clocks cannot be merged into “wait after cleanup.”

2. **Closing admission preserves prior ownership.** Queue wait10; call1 starts0, call2 waits, cleanup twice, then call3. Old P519 and P951 (composed as a proposed adjacent history) and A/B/C/D predict call3 fails with disposal reason and no row3, while call2 remains pending through9 and starts10. Rejecting old work, admitting3, flushing2, or treating cleanup return as completion is forbidden. The composition is reasoned, not an existing executed witness.

3. **Queue time and serial execution are distinct.** Queue wait10; enqueue1,2,3; hold handler1 beyond20; cleanup twice; release1 at20. P986–1060 expects only1 before release and then [1,2,3] (front) or [1,3,2] (back) after a zero-time microtask advance. Candidate B/C preserves this. A proposed extra10ms between handler starts would reject an explicitly accepted source witness. This is why “all persistence starts are always at least wait apart” is not an equivalent queue law. G1236's example shorthand is more general-sounding than this test; the precise public wording merits alignment, not changed assertions.

4. **Waiting capacity is not all unsettled work.** Hold first write; maxSize1, wait10; calls1,2,3 yields states persisting/pending/failed. Same maxSize with wait0 admits all three because scheduling removes waiting items while serial handlers remain blocked. maxSize0 rejects every call before first processing. P1148–1234 and A/B match. Counting every pending receipt as capacity would forbid a retained valid case.

5. **A rejected same-key caller is isolated.** Queue maxSize1/wait10: insert value1, admitted update2, overflow update3. Required visible value2; overflow rejects with capacity error. After first settles, second optimism remains value2 and its receipt is pending until its own handler settles. P1236–1313 and A/D agree. Leading-only debounce/throttle have analogous held value1/drop value2 witnesses P652–720. Blanket rollback/cascade would violate peer isolation.

6. **A return value is not a universal admission or settlement signal.** Custom queue schedules callback10 and returns void; custom batch schedules callback10 and returns false. Old P1315–1386 and A/D require pending transaction/optimistic row before10, then successful same-transaction settlement. A generic false/falsy-is-rejection formulation loses compatibility. Built-in explicit refusal remains distinct.

7. **Queue failure survives the coverage exclusion.** Queue1 and2 admitted;1 rejects with error E after cleanup;2 succeeds. Public G1261–1268 and candidate D require failure1/E, no automatic retry, and continued attempt2. Original paced grammar has no such path. Existing tests therefore provide no observed answer. Smallest next experiment: a held rejection followed by a succeeding peer, inspect the rejected receipt before releasing peer2, preserve no duplicate starts, and include same-key versus distinct-key peer isolation. This would challenge both failure continuation and rollback independence.

8. **Batch concurrency needs a missing distinction or design decision.** Leading throttle starts1 at0 and handler1 remains pending past10; call2 at4 schedules trailing edge10. G1099 promises at most one persisting transaction; timing text supplies a regular edge, and the oracle's immediate-handler schedules cannot choose precedence when the handler is held. Source `paced-mutations.ts:105–129` clears the active pending reference before committing; throttle callback at `throttleStrategy.ts:72–79` does not await the prior transaction. This suggests overlapping persistence, not an executed result. Candidate retains both sourced obligations and marks the interaction unresolved. Next experiment records active handler count and exact start/settlement order across the held edge, with/without cleanup; compare whether edge means eligibility or mandatory handler start under this premise. Similar leading debounce history is needed. If concurrency is intentionally permitted, changing G1099 is a product-contract correction with migration implications, not a preservation refactor.

9. **Settlement is not external confirmation.** Handler fulfills without a server sync row. G245–276 permits transaction completion and optimistic-state recomputation without server confirmation; D preserves it. “Drain succeeded means server confirmed every write” would strengthen the contract improperly. Conversely, handler intentionally awaiting confirmation must remain unsettled until that observation. Full publication behavior remains with optimistic-history ownership.

## Tension scan results

- **Cleanup versus admitted persistence:** no supported conflict once strategy cleanup, Collection sync-run cleanup, scheduled work, and transaction settlement are distinguished. The public sources explicitly retain work. A stronger invented promise of immediate total cancellation is unsupported.
- **Resource cleanup versus a retained timer:** BaseStrategy's general resource wording and built-in pending-work clauses do not specify the same release checkpoint. Eventual resource release remains an obligation; immediate release of a timer needed for admitted work is not established. Physical resource-release evidence is missing and must not be declared solved by successful transaction settlement.
- **Queue configured pace versus serial handlers:** a real wording ambiguity, resolved for the existing fixed witnesses by separating scheduled queue processing from serial handler starts. Keep both observations. Do not claim all arbitrary delayed schedules are settled.
- **Immediate optimism versus rejection:** no contradiction. The mutation is applied optimistically, then refusal rolls back its contribution. The meaningful preservation requirement is peer isolation, not a claim that a rejected row remains visible after the call.
- **Built-in false return versus custom callback retention:** scope distinction resolves apparent conflict. No universal BaseStrategy boolean meaning has authority.
- **Debounce/throttle concurrency versus execution edge:** open source-level interaction as described in witness8. It is neither a demonstrated runtime bug nor permission to remove either promise.
