## Findings

### P2 — Carry forward the explicit-false custom queue admission rule

**Challenged claim:** Candidate A:9–11 states built-in overflow rejection and preserves custom queue `void` and custom batch `false`, but does not state that an explicit `false` from a custom queue rejects admission.

**Original insight:** The meaning of an execution result depends on the strategy category. A queue's explicit `false` is a rejection signal; `void` is compatible with a callback retained for later. A batch's `false` can also retain work. Treating all falsey returns alike either rejects admitted custom work or strands a rejected queue transaction.

**Authority:** `packages/db/src/strategies/types.ts:66–72` expressly says “Explicit false rejects the transaction; void preserves custom strategies.” `packages/db/src/paced-mutations.ts:157–178` supplies the corresponding boundary, with `QueueCapacityExceededError` and isolated rollback. The paced owner's opening and custom witnesses at `paced-mutations-oracle.test.ts:1307–1386` preserve the contrasting `void` queue and `false` batch cases. Its overflow calibration at `1496–1532` demonstrates why reporting acceptance after a rejected enqueue is a relevant wrong design, although this review has not run that calibration.

**Distinguishing history:** Use a custom `_type: 'queue'` strategy whose `execute` returns `false` and retains no callback. Make one valid optimistic insert through `createPacedMutations`. At the admission cut, the original rule requires a failed returned transaction, rollback of its optimistic row, and rejection with `QueueCapacityExceededError`. No timer or persistence callback is needed. The candidate's generic sentence about “a rejected call” does not itself classify this call as rejected. An implementation that handles built-in overflow correctly but leaves this custom transaction pending is not expressly excluded by the candidate's custom-return clauses.

**Classification:** Unresolved/omitted classifier in the candidate, not an authorized retirement. Built-in capacity behavior is preserved. Source pointers and the no-retirement preamble suggest preservation was intended, but a replacement law should let the reader reconstruct this distinction without importing the missing classifier.

**Smallest repair:** Add to A: “An explicit `false` from a queue strategy rejects admission with `QueueCapacityExceededError`; `void` does not.” Keep the separate batch `false` exception. If executable coverage is subsequently extended, a custom queue with `false`, `void`, and a retained batch callback is the smallest receiving matrix; no new lifecycle model is necessary.

### P3 — Limit call-local rollback wording to strategy admission rejection

**Challenged claim:** Candidate A:7 says “A rejected call” removes only that call's optimistic contribution and preserves previously admitted same-key work. The section heading suggests admission, but the sentence does not say so. Candidate D:41 separately requires transaction failure to roll back its optimistic state.

**Original insight:** Rejected overflow, disposed-queue, and disabled-edge calls must not use cascading rollback to cancel previously admitted work. That is admission isolation. Calls sharing a debounce/throttle transaction are intentionally one failure unit after their merged transaction starts persistence.

**Authority:** `paced-mutations-oracle.test.ts:519–721,849–923,1240–1305`; `paced-mutations.ts:172–195`; `docs/guides/mutations.md:249–276,1099`; `optimistic-history-oracle.ts:13–18`.

**Distinguishing history:** With default debounce wait 10, call `a` at time 0 and `b` at time 4 to update the same row. Both receive the same pending transaction. At time 14, its merged handler rejects with error E. The transaction-settlement contract permits and requires rollback of that transaction's combined optimistic state; both callers observe rejection of the same transaction. Treating `b` as any “rejected call” whose earlier admitted same-key `a` must remain intact would require a new per-call failure policy and conflict with shared transaction identity.

**Classification:** Preserved under the intended admission reading; accidentally strengthened under an unqualified persistence-failure reading. This is a prose ambiguity, not evidence that the candidate intentionally adopts new policy.

**Smallest repair:** Change “A rejected call” to “A call rejected at strategy admission,” and scope “Previously admitted same-key work remains intact” to that rejection. Do not generalize this sentence to handler failure. No execution is needed to make this editorial repair.

## Legal implementation freedom and apparent tensions

1. **Scheduled processing versus handler starts:** B correctly permits already scheduled queue work to start close together after a held transaction settles. The guide's informal queue example “500ms between them” cannot override the explicit waiting-item and serialization laws plus the distinguishing held-backlog witness. No additional rate-limit policy should be inferred.
2. **Cleanup resources versus persistence:** BaseStrategy says to clean up resources, while built-in docs explicitly retain admitted work. The candidate neither retires resource cleanup nor invents synchronous disposal. It is valid to retain resources needed for admitted work and release them later. Exact resource-release evidence and the full lifecycle of every resource remain outside the supplied pacing tests.
3. **Collection cleanup versus scheduled callbacks:** A Collection sync run loses publication authority during cleanup, but that does not turn an independently admitted pacing callback into a canceled write. The candidate keeps those owners separate and does not merge their executable models.
4. **A promised concurrency bound versus an elapsed edge:** The guide's one-persisting bound is not optional because the oracle lacks a held-handler case. Candidate B:25 explicitly preserves it. Source inspection of `paced-mutations.ts:118–124,137–145` and built-in timer callbacks predicts that an additional transaction can start while an earlier one is held; this is an unexecuted implementation concern, not evidence that the policy is unsettled in the sense of being optional. The timing interaction requires an explicit contract resolution or implementation conformance work.
5. **“Every mutation persists” shorthand:** The guide's strategy-choice slogan cannot mean every handler succeeds or the backend necessarily confirms. The adjacent precise rules explicitly reject overflow, allow handler failure, prohibit automatic retry, and promise attempts for admitted mutations. Candidate B/D preserve that necessary distinction.
