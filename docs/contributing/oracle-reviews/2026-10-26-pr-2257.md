## Findings

### P2: Generate cleanup during partial delivery and reset

Location: `packages/electric-db-collection/tests/electric-sdk-delivery-oracle.property.test.ts:2415-2417`, with the response driver at 2337-2359.

Every successful generated response includes both a row and `up-to-date`.
Consequently `cleanup-while-loading` means no delivered rows or only retries;
it never includes a transaction opened by a partial row batch, or an active
reset awaiting replacement data. The law promises listener release whatever
state the source reached. These are legal ordinary stream histories:
`electric-sdk-framing.test.ts:29-35` already demonstrates row-only responses
and HTTP 409 `must-refetch` delivery through the real SDK.

Two single-condition changes to the production cleanup pass the existing
fixed/random listener campaigns and managed-cache rotation case:

```ts
if (!transactionStarted) stream.unsubscribeAll()
// Separately:
if (!isResettingSnapshot) stream.unsubscribeAll()
```

The first also passes all 42 existing SDK delivery tests. A row-only response,
next actual HTTP request, then cleanup distinguishes the first change: the PR
leaves zero listeners; the incorrect variant leaves one. An initial HTTP 409
`must-refetch`, next actual request, then cleanup distinguishes both changes
in eager, on-demand, and progressive modes. The Collection remains `loading`
before cleanup, and the final listener comparison is the failing assertion.

Repair the primary history grammar with row-only and reset answers separate
from `up-to-date`. Permit cleanup before that later marker and declare reach
for partial-delivery and reset cleanup. Include nearby retry, give-up, abort,
and restart histories when claiming coverage of the full stated class. Keep
the independent active-run model; do not copy production transaction/reset
flags into it. This finding concerns oracle coverage. The PR's unconditional
production release passes these cases.

### P2: Release retained listeners after a failing test

Location: `packages/electric-db-collection/tests/electric-sdk-delivery-oracle.property.test.ts:331-334` and 2396-2401.

The recorder's `restore()` restores method spies but leaves any remaining DOM
listener registered. With the original missing release, Collection cleanup
already completed; repeating that idempotent cleanup cannot remove the
listener. Thus each failing or shrinking run leaves the dead SDK stream
reachable from the shared document. ORC-010 requires test resources to be
released on failure too.

A direct real-SDK/jsdom diagnostic recorded one actual listener after the
original cleanup, one after exact recorder restoration, and zero after
explicit SDK release. This is a diagnostic plus source tracing of the test's
cleanup path, not a complete generated-campaign teardown experiment.

Preserve the primary assertion, then remove remaining registrations owned by
the recorder during final teardown, or retain stream handles for independent
test cleanup. Add a deliberate failure case showing both the original
mismatch and final resource release. Do not remove listeners before comparing.

The oracle grammar now accepts zero to three answers per run, from `row`,
`up-to-date`, `reset`, and `retry`; one to three runs; all three sync modes;
and open, give-up, or abort endings. The same driver also runs 18 minimal
histories: two incomplete answers × three endings × three modes. These remain
replay examples alongside generated nearby histories, rather than replacing
generation. Readiness reach reads public Collection status; pending-answer
reach derives only from provider inputs, without inspecting production
transaction/reset flags.

Grammar controls: removing row-only or reset loses the demonstrated cases;
removing up-to-date loses completed-delivery comparisons; removing retry loses
incomplete delivery across retried failure; removing terminal endings loses
give-up/abort cleanup; removing modes loses their installed-SDK paths; removing
multiple runs loses cleanup/restart and already-aborted restart. Zero answers
covers immediate cleanup, three answers can cross reset, row and completion,
and three runs cover repeated release. Requests are answered only when the
real SDK sent them: after give-up or external abort, no later response is
invented. This is a bounded grammar, not a proof for arbitrary history length.
