## Claim and boundary

The Collection sync-adapter contract and Query Collection guide require an
accepted acquisition to keep its observer lease until release. Its successful
load must have its source row applied at settlement. Before acceptance, caller
abort rejects that caller and prevents its unaccepted row from publishing. A
peer keeps shared Query work alive; after acceptance, the transaction applies
even if that caller aborts. Collection cleanup can instead abandon a pending
accepted receipt. Query DB owns the Query instances in this claim. The
[repair plan](2026-10-15-query-db-lifecycle-repair-plan.md) records the
same-object release decision and the ten-finding review audit.

The checked boundary is **contract × histories × production path × public
observations**: the named and generated acquisition, final-release, callback
reentry, accepted-commit, and refetch histories run through real Collection and
QueryClient APIs; the comparisons inspect each promised load outcome, receipt
application, full public rows, physical signal, and observer lifetime at the
held-provider, held-receipt, settlement, and final-release checkpoints. The
persisted owner additionally checks durable rows and retention markers across
its named restart histories.

The four original expected failures on `b5c55a2a4` became ordinary passing
tests. The reentrant release grammar rejected the old implementation in
equal-scope histories, and the original caller-abort path failed at the public
load, signal, and row checkpoints. Later overlap witnesses rejected the
intermediate implementations: the fetching successor failed on `5e90ac9c9`
and the paused successor failed on `43551b835` while B's accepted receipt was
held. The overlap oracle now records receipt application and the complete
public row set inside B's rejection callback. Separate wrong-result controls
with an unapplied receipt or A's rows fail that exact comparison.
The refetch grammar similarly requires prompt `AbortError` while its provider
is held; a delayed-abort wrong-result control fails there.

The remaining unproved overlap cells are arbitrary chains of reentrant
successor fetches, provider failure during that overlap, and storage at that
same callback cut. They belong to the load-lifecycle and persisted owners in
the [coverage map](../oracle-coverage.md). No reachable in-scope
counterexample was confirmed by the exact-head reviews. The distinct
non-source-result provenance failures remain in
[issue #2176](https://github.com/TanStack/db/issues/2176); this PR does not
repair that contract boundary.
