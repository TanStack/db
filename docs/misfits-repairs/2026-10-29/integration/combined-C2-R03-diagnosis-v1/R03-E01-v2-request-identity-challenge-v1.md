# E01 v2 request-data versus logical-owner challenge

This read-only challenge concerns frozen primary `1e97eae555c2a649d6acd793f7d6d8e591b13dc4a5c50d753550c945d2e44e41`, especially the same-subscription/same-where exception in settleParticipant. It supplements, rather than replaces, the C1/C2 record `d983a99aab930ca5cf183eabf70182d8ff4281135c406072b9f96fb1050488be`. No runtime or source edit is performed.

Author's exact implementation question:

> Implementation decision check: an actual same-request retry can be issued via requestSnapshot with original where object on the same subscription while A stays held and B remains pending. This creates a new logical subset owner; same predicate identity alone may not authorize replacing A under lifecycle replacement relation. E2 publication already permits same subscription + exact where as retry, but is that accepted logical-demand identity or should same-request successful retry use an explicitly authored replaceSnapshots relation even with same where? I will not equate a duplicate owner with a retry merely from key/predicate overlap. Other new pre-freeze histories will keep A held while unrelated complete success or explicit replacement failed later settles before B.

Independent response: equal request data does not establish equal logical owner. The glossary's demand graph and table distinguish demand, logical subset owner, request data and acquisition attempt; the primary lifecycle grammar's opening defines request as a new logical owner plus its acquisition. Actual startSubsetDemand1164 constructs a new demand on every requestSnapshot invocation, which is receiving evidence consistent with that authority. A duplicate request on the same subscription with the same predicate object therefore cannot, by that identity alone, erase the failed held owner's obligation.

Use distinct immutable request identity and an explicitly authored replacement relation for a new equivalent-key owner that replaces held coverage. Do not silently call that duplicate owner a retry. A genuine new attempt for an existing owner instead needs independently established acquisition abort/supersession/retirement semantics; those may end the earlier attempt's obligation without equating logical ownership to predicate equality. Same-where replaceSnapshots also has a concrete receiving ambiguity: its find(where) can select the earlier matching demand instead of the new duplicate, so it is not evidence of the intended edge without a distinguishable binding.

This finding challenges v2's same-where publication exception as well as the proposed completion correction. It does not impose identical publication and immutable-completion predicates, and does not infer expected authority from production-installed edges. It remains open for the separately frozen enforcement successor, its legal controls and exact finite recipe review. Root and author were notified.
