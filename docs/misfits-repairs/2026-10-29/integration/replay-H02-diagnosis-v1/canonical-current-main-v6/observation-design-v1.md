# V6 allocation and retention limits

This is a source inventory of the frozen instrument, not an allocation profile. No heap snapshot, allocation counter, retained-size measurement or garbage-collection reachability probe ran. The receiving worker's native heap failure cannot yet be attributed to production or to instrumentation.

The receiving receipt writer retains a file descriptor, sequence/byte counters and failure state. It constructs a JSON string and Buffer for each receipt, then writes every byte synchronously. It keeps no all-receipt array. These are still repeated allocations and synchronous I/O on the production thread; absence of a retained log array does not establish negligible overhead.

The source instrument retains startup URL/script-ID/hash metadata and sealed module keys. Full V8 bodies remain on disk. The startup seal checks them, disables the debugger and disconnects before drive. No precise profiler runs during the history. Registry inventories are captured at startup, driver start and the reached premise; no per-acquisition source inventory is accumulated. These statements describe storage design, not measured retained heap or proof that engine debugging metadata was reclaimed.

The driver keeps latest query-scope, completed-answer and installed-answer records by query hash, actual subscription identities by Map, physical Query tokens and acquisition-attempt bookkeeping by WeakMap, a pending-provider-request array, and small stack/scope flags. Completed/installed provenance records strongly reference their corresponding Query. Pending-provider records are retained for the driver's lifetime rather than removed after release. The raw trace contains 13 provider requests, five after reload began, versus 14,187 actual acquisition attempts; the arrays/maps must not be assumed equivalent to per-acquisition retention counts. A WeakMap does not retain its keys by itself, but this run did not measure whether production or other references kept those keys alive.

The actual-state detector creates snapshots while seeking the premise. After queue admission it returns immediately before scanning or copying Query state. The first repeated-acquisition diagnostic and post-queue stack each capture once. Key/callback/acquisition receipts continue allocating and writing on every observed event. The driver uses the same finite provider-answer release behavior as before; source reading alone cannot establish which repeated objects survive the synchronous feedback.

The parent file reader is a separate process. It retains a partial-line fragment, a 64 KiB read buffer per drain, scalar counters and the existing small semantic-receipt subset. The parent comparison keeps its modeled/public event state. The offline verifier's complete raw-receipt array is allocated only in a separate sequential process after the receiving group exits. Neither process is the receiving worker PID 75057 that exhausted its 384 MiB heap; this does not exclude host resource/timing effects.

Existing containment is unchanged: receiving Node heap 384 MiB; group RSS sampled every 100 ms and killed if above 1 GiB; wall watchdog checked by that same parent interval and killed after 20 s; outer canonical test 60 s; offline verifier sequential 20 s/384 MiB. These are instrument containment limits, not product deadlines. Native heap exhaustion occurred before the wall/RSS watchdog fired. No kill was attempted. The source monitor retained its generic exited/nonzero-without-worker-error classification; the full raw stderr supplies the explicit heap diagnosis.

Observed result: one real conflict premise and one completed host enqueue receipt, followed by no answer-executed receipt before heap termination. This is a resource-limited finite prefix. It is neither a product RED nor a product GREEN, and it does not establish eventual non-completion, a product allocation leak, an instrumentation leak, or closure. A concrete cause and an admissible judgment remain open before production changes.
