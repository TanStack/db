## Source trigger hold and continuation-specific gaps

The positive held-provider read is feasible now and is included in the staged driver. It does not establish the proposed D2 suspension trigger. Current production has no continuation scheduler or token to observe or hold.

The separate [completion API v3 design](../design-review/queued-answer-progress-completion-api-v3.md), SHA256 `c53e3bf3767b0bff451d0c05541b31e0a5e51e569e039634a163f42f2803b0e1`, section 4 defines the later seams. Every following reach is **UNREACHED** here:

- Existing publication hold captured before demand update; changed Promise-returning demand; synchronous input revision advances; D2 has actual remaining work after a complete operator.
- Exact builder-owned continuation token is enqueued. The answer microtask executes and the final demand settles before that token runs. Existing window Promise remains pending, and `getWindow()` plus public rows keep the settled snapshot.
- A new partial-options window call in that asynchronous gap is admitted, inherits active requested options, and remains pending until its chosen result is visible.
- Repeated yields, ties and refills preserve the same completion obligation. A graph pass with `flush = held` cannot complete it.
- Root or touched-facade output receipts remain parked, including output queued before suspension. Completion waits for their public visibility and the current input/window revision check.
- A resumed terminal graph or publication error rejects the operation with the exact deciding error while a source peer never answers. A recoverable demand error retains existing aggregation and replay-retention meaning.
- Cleanup/restart, newer truncate or reentrant lifecycle change invalidates the old task and receipt callbacks. They cannot alter a replacement continuation record.

Do not intercept all timers. Query Core and this driver use independent host tasks. Later instrumentation must bind its hold to the candidate builder-owned callback/token, or a separately reviewed narrow internal scheduler function. A normal driver host turn is not evidence of suspension.

The current patch does not add these candidate-specific observations to a different model. Their receiving source and shared operation/publication judgment must be prepared and accepted before a production edit. The original starvation mutant must fail the progress comparison; an early-window-success mutant must fail the publication comparison. No such new mutant was run here.
