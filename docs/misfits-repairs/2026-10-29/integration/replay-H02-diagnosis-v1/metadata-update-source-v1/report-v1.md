## Complete observation cut

For the canonical positive follow-up, the established reload changes the
selected row4/rank40 to row3/rank30. Only after its settled final baseline does
the source write change row3/rank30 to row3/rank35. The owed output message at
both layers is an actual same-key update with row3/rank30 as `previousValue`.
Missing previous value, the full new row, and the older row4 reload baseline
are distinct wrong observations.

Changing an order term may start repair even though its relative position is
unchanged. The driver therefore waits for the source applied receipt, every
actual follow-up acquisition's applied settlement, ready output subscriptions,
no output subset load, no pending provider answer, idle observed Queries, and
actual callbacks at both layers for a positive update. Stable host turns only
drain later work; they cannot establish this cut alone. The parent then checks
every callback read, the accumulated exact message delta and both final
snapshots. Any partial result, retained-key failure or absent update blocks
semantic reach.

The backend remains finite during follow-up: the original queued callback
records `answer-executed`, sets `holding = false`, and releases pending answers.
The completed reload and its baseline drain occur later. No assignment sets
`holding` true between that callback and the source follow-up. A new provider
request therefore takes the existing immediate finite `complete()` path.
This is a source invariant to verify at native receiving cuts, not new runtime
evidence.
