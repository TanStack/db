## The synchronous cycle

These source paths are read at the frozen worktree HEAD `9cfa11fc712866f8f276e85762865ebb8bd49cbe`. Query Core is the frozen installed 5.90.20 package. The chain explains repeated acquisitions without assuming every hidden state repeats.

1. With marker 3 absent, the anti-join admits root 3. Offset 1 / limit 1 selects it after unmatched root 2. Its inline include derives demand for marker scope `[3]`. The compiler's parent-key tap calls `setDemand` inside the D2 pass (`packages/db/src/query/compiler/index.ts:873–895`).
2. `SubsetDemandController.setDemand` installs the new segment and calls `startSegment`; `startSegment` calls the subscription's public `requestSnapshot` (`subset-demand-controller.ts:142,330`). Core installs tentative acquisition ownership before the adapter call (`collection/subscription.ts:1238–1243`).
3. The include's subscription key is `["h02-progress-markers",2,[3]]`. Query DB recreates an observer on the same cached physical Query 4. That Query retains backend-v0 cached row 3 while its backend-v1 request is pending. `subscribeToQuery` subscribes and immediately processes the current successful result (`query-db-collection/src/query.ts:3389–3404`). The fetch can remain asynchronous while cached ownership applies synchronously.
4. `applySuccessfulResult` claims the cached row and writes its insert when the source Collection no longer holds it, then commits (`query.ts:2792,2812`). `requestSnapshot` also reads the current Collection state immediately after acquisition (`collection/subscription.ts:1400–1452`); it does not await the returned Promise.
5. Source publication sends deltas into the graph before scheduling another graph run (`collection-subscriber.ts:270–290`). `maybeRunGraph` suppresses a nested invocation while its graph is running (`collection-config-builder.ts:822–827`), but the deltas already reached the D2 input. `D2.run` repeats synchronous operator passes until no operator ran; it has no host yield (`db-ivm/src/d2.ts:65–79`).
6. Marker 3 now makes root 3 fail the anti-join. The window loses its selected parent, and the include's demand becomes empty. The demand controller removes that plan and releases its segment (`subset-demand-controller.ts:110–118`). Core removes logical ownership and releases the acquisition once, aborting its signal and invoking Query DB unload (`collection/subscription.ts:1517–1545,1170–1183`).
7. On final observer ownership release, Query DB unsubscribes, removes ownership, and deletes row 3 if no peer owns it (`query.ts:3497–3548`). The already fetched sibling key `["h02-progress-markers",1,[3]]` has empty backend-v1 data, so it supplies no row-3 ownership. Query Core emits `observerRemoved` during unsubscribe before Query DB's later ownership delete. V6's last receipt is therefore not proof that this last delete finished.
8. The delete feeds the anti-join again. Root 3 qualifies, recreating its include demand. The current D2 pass can consume this input without returning to the host. Graph publication remains after graph quiescence (`collection-config-builder.ts:859–889`); no public partial-row shortcut is authorized.

The two cached versions are conflicting acquisition baselines, not a new ownership law. Immediate cached ownership on reacquisition remains required. Deferring the cached insert, silently treating a Promise as literal true, or flushing between partial graph passes would evade neighboring laws.

## What can change or end this cycle

The queued driver callback is the only post-enqueue driver action that clears `holding` and releases all held provider answers. Its first action emits `answer-executed` (`queued-answer-progress-driver.ts:273–290`). The provider's held Promise has no abort handler; aborting an acquisition does not invoke its `release` function. Promise reactions and timers require a host scheduling opportunity.

Query Core has a concrete cancellation alternative: removing its last observer cancels and reverts a retryer if the Query fetch signal's lazy getter was consumed; otherwise it cancels retries and keeps the fetch alive (`@tanstack/query-core/src/query.ts:354–374`). A later fetch returns that live retryer Promise (`query.ts:390–408`). The driver reads the original acquisition signal from request metadata, not QueryFn `context.signal`. Query DB preserves that lazy getter and uses a shared signal only under its documented peer/released-signal conditions (`query-db-collection/src/query.ts:2235–2295`). No new provider request or cache-success receipt follows the request immediately before conflict 214. The surviving pending fetch is therefore supported by observations; a spontaneous authoritative answer change is not.

Other source-level exits are graph quiescence, a synchronous throw, cleanup or sync-run invalidation reached reentrantly, or a source/ownership change that removes the feedback. No acquisition/pass cap, timer expiry checked by D2, or finite provider countdown is present. The fixture schedules no external post-enqueue mutation before the resolving callback. Query-cache GC is disabled by `gcTime: Infinity`. Native termination is a real exit but does not execute the queued answer.

Hidden state is not fully observed: weighted operator indexes, fractional-order state, replay participant identity, application controllers and Promise queues can change while the visible key/scope repeats. A later finite transition is not logically excluded by four captured stacks. No concrete lawful finite transition that resolves this held answer without host execution has been identified. A full native-state cycle proof is not an additional gate in the accepted bounded-watchdog plan.
